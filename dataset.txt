=====================================================================================
The dataset utilized across all experiments in this project is the TAWOS
(Technical and Agile Work-item Open Source) dataset. TAWOS is a comprehensive,
public benchmark dataset curating historical work items and issue-tracking
records from industrial and open-source software engineering repositories
managed under Atlassian Jira.

Academic Metadata & Citations:
  * Dataset Name:       TAWOS (Technical and Agile Work-item Open Source)
  * Primary Archive:    University College London (UCL) Research Data Repository
  * Dataset DOI:        10.5522/04/21308124
  * Raw Distribution:   TAWOS.sql (MySQL Relational Database Dump)
  * Raw File Size:      4,313,856,480 bytes (~4.02 GB uncompressed)
  * Issue Tracking:     Atlassian Jira
  * Project Domain:     Agile Software Engineering (Story Point Estimation)
  * Temporal Range:     July 8, 2004 to October 22, 2020 (16+ years of history)
  * Total Projects:     39 Distinct Software Systems
  * Total Raw Issues:   427,330 Records
  * Valid SP Issues:    63,003 Records (Non-null text, valid dates, Story Point > 0)

Significance for Problem Statement 4:
Problem Statement 4 specifically mandates evaluating BERT-based word embeddings
for predicting story points of later issues in a target project using source-project
training data and chronological ordering. TAWOS provides the required real-world
longitudinal agile issue descriptions, developer estimation labels (story points),
and exact chronological timestamps needed to execute cross-project forward-chaining
evaluations without artificial data leakage.

2. RAW RELATIONAL DATABASE SCHEMA & ARCHITECTURE (TAWOS.sql)
=====================================================================================
The primary source file TAWOS.sql is a single massive MySQL relational dump.
Rather than relying on an external MySQL database service (which introduces
heavy socket overhead and platform dependency), the codebase parses the raw dump
directly via high-speed binary byte offsets and multi-process streaming.

Database Architectural Offsets:
  * Total SQL Byte Length:     4,313,856,480 bytes
  * Issue Table Offset:        3,257,392,906 bytes (approx byte 3.25 GB)
  * Project Table Offset:      4,310,524,095 bytes (approx byte 4.31 GB)

Primary Relational Tables:
1. Project Table (9 Fields):
   - ID:                  Integer Primary Key (e.g., 1, 2, ..., 44)
   - Project_Key:         Short uppercase Jira project key (e.g., XD, MESOS, TIMOB)
   - Name:                Full canonical database project name (e.g., "Spring XD")
   - URL:                 Jira repository endpoint URL
   - Description:         Textual description of the software repository
   - Start_Date:          Project inception timestamp (ISO format)
   - Last_Update_Date:    Latest repository synchronization timestamp
   - SP_Field_ID:         Custom field identifier mapped to Story Points in Jira
   - Repository_ID:       Underlying version control link ID

2. Issue Table (30 Fields):
   - ID:                  Unique integer primary key across all TAWOS issues
   - Jira_ID:             Upstream Jira issue database ID
   - Issue_Key:           Compound ticket key (e.g., "XD-3768", "MESOS-124")
   - URL:                 Direct URL to upstream Jira ticket
   - Title:               One-line summary of the bug, feature, or task
   - Description:         Raw Jira issue description (may include markup)
   - Description_Text:    Extracted plain-text description
   - Description_Code:    Isolated code blocks extracted from description
   - Type:                Issue type (Bug, Improvement, New Feature, Task, Sub-task)
   - Priority:            Priority rank (Blocker, Critical, Major, Minor, Trivial)
   - Status:              Workflow state (Closed, Resolved, Done, In Progress)
   - Resolution:          Resolution reason (Fixed, Won't Fix, Duplicate, Done)
   - Creation_Date:       Timestamp when the issue was filed (ISO timestamp)
   - Estimation_Date:     Timestamp when story point estimation was assigned
   - Resolution_Date:     Timestamp when the issue was resolved/closed
   - Last_Updated:        Timestamp of most recent issue modification
   - Story_Point:         Numerical agile effort estimation (Primary Target Variable)
   - Timespent:           Logged developer effort in seconds
   - In_Progress_Minutes: Active work duration in minutes
   - Total_Effort_Minutes:Cumulative logged minutes
   - Resolution_Time_Minutes: Wall-clock minutes from Creation to Resolution
   - Title_Changed_After_Estimation: Boolean flag indicating retroactive edit
   - Description_Changed_After_Estimation: Boolean flag for description changes
   - Story_Point_Changed_After_Estimation: Boolean flag for re-estimation
   - Pull_Request_URL:    Linked GitHub/Git pull request URL if present
   - Creator_ID:          Foreign key identifier for issue reporter
   - Reporter_ID:         Foreign key identifier for issue logger
   - Assignee_ID:         Foreign key identifier for assigned developer
   - Project_ID:          Foreign key linking to Project table (1 to 44)
   - Sprint_ID:           Foreign key linking to Agile Sprint entity

3. INGESTION, FILTERING & PREPROCESSING PIPELINE (extract_data.py)
=====================================================================================
The high-performance extraction pipeline in `src/extract_data.py` implements a
deterministic, multi-stage filtration protocol to produce clean CSV deliverables.

Extraction Pipeline Flow:
  1. Binary Seek: Jumps directly to Project table offset (4.31 GB) and parses
     all 39 active software projects in under 0.05 seconds.
  2. Streaming Multi-Core Parse: Streams the 3.25 GB Issue partition using a pool
     of worker processes parsing SQL INSERT VALUE tuples without intermediate DB.
  3. In-Flight Cleansing & Filtration:
     * Valid Story Points: Discards issues with NULL, NaN, or non-positive story
       points (Story_Point <= 0). In Jira systems, ~85.25% of all filed tickets
       (364,327 issues) are unestimated bugs, questions, or triage placeholders.
       Retains exactly 63,003 valid issues with positive numerical estimates.
     * Non-Empty Text: Ensures each ticket contains a non-empty semantic signal
       by combining Title and Description_Text.
     * Parseable ISO Timestamps: Validates Creation_Date against standard
       YYYY-MM-DD HH:MM:SS format to guarantee temporal ordering.
  4. Deliverables Output: Outputs cleaned datasets to `data/processed/` and mirrors
     them to repository root:
     * issues.csv:           63,003 rows x 9 columns (61,116,794 bytes, ~61.1 MB)
     * projects.csv:         39 rows x 7 columns (3,805 bytes)
     * project_mappings.csv: 39 rows x 10 columns (4,877 bytes)

Standardized Schema of Extracted issues.csv:
  1. issue_id:        Original integer primary key from TAWOS database
  2. issue_key:       Compound Jira ticket key (e.g., "XD-3768")
  3. project_id:      Internal integer ID of the parent project (1 to 44)
  4. project_name:    Guideline-standardized project name (e.g., "XD", "Evergreen")
  5. title:           Raw ticket summary/title string
  6. description:     Raw ticket description string
  7. clean_text:      Standardized, cleaned text (Title + Description, markup stripped)
  8. story_point:     Agile effort score (target variable, floating point > 0)
  9. creation_date:   Timestamp string used for strict chronological ordering

5. THE 4 MANDATORY CANONICAL DATABASE MAPPINGS & RATIONALE
=====================================================================================
Discrepancies exist between project names printed in Project Guidelines.pdf
and table values in TAWOS.sql. To ensure 100% bijective coverage and rigorous
scientific reproducibility, four inviolable canonical mappings were formalized
and enforced throughout the codebase:

Rule 1: "Evergreen" -> "The MongoDB Engineering" (Project ID 43, Key EVG)
  - Context & Rationale: Evergreen is MongoDB's automated continuous integration
    and testing platform. In the upstream TAWOS database, issues for this system
    are stored under the umbrella Jira project name "The MongoDB Engineering" with
    issue key prefix EVG-. This project contains 10,299 raw issues, of which
    5,069 issues have valid story points (SP > 0).

Rule 2: "C++ driver (Appcelerator)" -> "Aptana Studio" (Project ID 8, Key APSTUD)
  - Context & Rationale: Appcelerator acquired Aptana in 2011 to integrate the
    Aptana Studio IDE into the Titanium mobile development ecosystem. In the
    database, Appcelerator's C++ tooling issues are recorded under "Aptana Studio"
    with key prefix APSTUD-. It contains 8,135 raw issues and 839 valid SP issues.

Rule 3: "C++ driver (MongoDB)" -> "The Mongo C++ driver" (Project ID 31, Key CXX)
  - Context & Rationale: The guidelines refer to this system as "C++ driver (MongoDB)",
    whereas the database names it "The Mongo C++ driver" with key prefix CXX-.
    It contains 2,032 raw issues and 212 valid SP issues.

Rule 4: "Java driver" -> "The Mongo Java driver" (Project ID 32, Key JAVA)
  - Context & Rationale: The guidelines specify "Java driver", which maps directly
    to "The Mongo Java driver" with key prefix JAVA- in the TAWOS database.
    It contains 3,560 raw issues and 238 valid SP issues.

Database Mappings Verification Table:

Analysis of Heavy-Tailed Distribution & Justification for MdAE:
1. Over 80% of all software tickets in the dataset cluster tightly around standard
   Fibonacci agile numbers: 1.0 (22.3%), 2.0 (19.0%), 3.0 (14.1%), 5.0 (11.9%),
   and 8.0 (8.3%). The median story point across all 63,003 issues is exactly 3.0.
2. Heavy-Tailed Right Skew: A tiny fraction of issues represent massive epics, long-term
   architectural milestones, or legacy time-tracking entries (e.g., 40, 100, or
   thousands of points).
3. Arithmetic Mean Distortion: Because absolute residuals are squared or averaged linearly,
   a single error on an epic (e.g., predicting 20 points for an issue that was
   labeled 100 points) introduces a massive 80-point error that artificially inflates
   Mean Absolute Error (MAE).
4. Median Absolute Error (MdAE) is robust to outliers, accurately reporting the
   median error experienced on everyday software sprint tickets (~2.8 to 3.2 points).
   This directly answers Section 3.4 of the guidelines regarding why MdAE is lower than MAE.

8. TEMPORAL ORDERING & ZERO DATE LEAKAGE PROTOCOL (PROBLEM STATEMENT 4)
=====================================================================================
In accordance with Section 3.2 of Project Guidelines.pdf, random train/test
splitting is strictly prohibited because it scatters tickets from contemporaneous
sprints into both train and test partitions, creating artificial data leakage.

Temporal Splitting Mathematical Formulation:
For each cross-project pair (Source Project S, Target Project T):
  1. Source Development Set (80%):
     Source issues are sorted chronologically by Creation_Date:
       t_1 <= t_2 <= ... <= t_{N_{dev}}
     The earliest 80% of issues constitute the Development Set D_source.
  2. Target Held-Out Test Set (20%):
     Target issues are sorted chronologically by Creation_Date.
     The most recent 20% of issues constitute the Held-Out Test Set T_target.
  3. Inviolable Zero Date Leakage Invariant:
     All training/validation timestamps precede test timestamps:
       max(Creation_Date(D_source)) <= min(Creation_Date(T_target))
     Verified: Zero Date Leakage = True across 100% (39/39) of evaluated pairs.
  4. Inviolable Zero ID Overlap:
     No issue ID appears in both training/dev and test sets:
       D_source intersect T_target = empty set
     Verified: Zero ID Overlap = True across 100% (39/39) of evaluated pairs.

5-Fold Expanding-Window (Forward-Chaining) Validation Protocol:
To evaluate validation performance on D_source without temporal leakage, the
development partition is split into 6 equal chronological blocks (B1 to B6):
  * Fold 1: Train on Block B1 (16.7%), Validate on Block B2 (16.7%)
  * Fold 2: Train on Blocks B1+B2 (33.3%), Validate on Block B3 (16.7%)
  * Fold 3: Train on Blocks B1+B2+B3 (50.0%), Validate on Block B4 (16.7%)
  * Fold 4: Train on Blocks B1+B2+B3+B4 (66.7%), Validate on Block B5 (16.7%)
  * Fold 5: Train on Blocks B1+B2+B3+B4+B5 (83.3%), Validate on Block B6 (16.7%)
Total Temporal Walk-Forward Folds across 39 pairs: 39 x 5 = 195 Folds (100% verified).
